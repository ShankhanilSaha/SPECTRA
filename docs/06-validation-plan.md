# 06 — Validation & Test Plan

**Named deliverable** of the problem statement.
**Purpose:** establish, in advance and in writing, how SENTINEL is proven correct — so
that an examiner asked *"has your tool been tested, and how do you know it works?"* has
a signed document to hand over instead of an opinion.
**Method basis:** NIST CFTT-style methodology (documented requirements → test
assertions → reproducible test cases → published results, including failures).

---

## 1. Validation philosophy

Four rules that make this document worth more than a test suite.

1. **Requirements first, tests second.** Every test case traces to an FR/NFR/AC in
   [doc 2](02-prd.md). A test that traces to nothing is deleted; a requirement with no
   test is a gap and is listed as one.
2. **Ground truth or it does not count.** "The video played" is not a result. "The
   recovered clip's SHA-256 equals the reference ES SHA-256" is. Every test case names
   its oracle.
3. **Publish the failures.** A validation report listing only passes is not credible.
   Known limitations are a section, and the tool's own output must reflect them.
4. **Negative testing is mandatory.** Corrupt images, wrong-vendor images, truncated
   images, and tampered audit logs must produce a *correct refusal*, not a plausible
   wrong answer. **A confident wrong answer is the only truly disqualifying failure
   mode in forensic software.**

---

## 2. Scope

**In scope:** functional correctness of identification, acquisition, parsing, decoding,
recovery, timestamp handling, correlation, integrity, reporting, and analytics framing;
the NFR performance and read-only guarantees; and determinism.

**Out of scope:** the accuracy of the third-party ML models beyond a documented baseline
(they are lead-generation aids, doc 1 §4.9); FFmpeg's own decoder correctness (pinned
and version-recorded, treated as a known component); hardware write-blocker
certification (the vendor's).

---

## 3. Test corpus

The corpus is the foundation. Building it *before* the parsers is not optional — a
parser with no ground truth cannot be validated at all, and hardware lead times mean
the synthetic tier is what unblocks development (doc 1 R1).

### 3.1 Tier S — Synthetic images (built by `tools/make_corpus.py`)

Small (100 MB–2 GB), fully specified images generated by writing structures we control:

| ID | Description | Ground truth available |
|---|---|---|
| S-01 | Dahua-family layout, 4 channels, 24 h, no deletions | Every recording's channel, start, end, byte extents, and per-clip ES SHA-256 |
| S-02 | S-01 with 30 % of index entries marked free, blocks intact | Exact list of orphan recordings — the T2 oracle |
| S-03 | S-01 with 20 % of blocks partially overwritten | Exact surviving byte ranges — the T3 oracle |
| S-04 | Hikvision-family layout, master sector + both HIKBTREE copies | As S-01 |
| S-05 | S-04 with the **primary HIKBTREE corrupted**, backup intact | Tool must use the backup and report that it did |
| S-06 | Bad-sector image: 2 % of LBAs unreadable, positions known | Exact bad LBA list; survivable spans — the T4 oracle |
| S-07 | Known clock offset of +00:17:42, timezone UTC+05:30 | Exact true UTC for every frame — the timestamp oracle |
| S-08 | **Clock changed mid-recording** (device clock set back 2 h on day 3) | Two-segment offset ground truth |
| S-09 | Truncated image (cut at 60 %) | Must parse what exists, report the truncation, not crash |
| S-10 | Wrong-vendor image (Hikvision structures with Dahua magics) | Must report ambiguity, **not** confidently pick one |
| S-11 | Empty/never-recorded disk | Must report zero recordings, not fabricate |
| S-12 | Multi-disk array member 2 of 3 | Must detect and require siblings |

Synthetic images are also the **regression corpus**: they are small enough to live in
the repo, run in CI, and catch a parser regression in seconds.

### 3.2 Tier R — Real-device images

Produced by the doc 4 §11 procedure on hardware the team owns. Ground truth comes from
controlled recording: a GPS-synced clock in frame, distinct scenes per channel, recorded
start/stop wall-clock times.

| ID | Device | Ground truth method |
|---|---|---|
| R-01 | Dahua-family unit, fresh format, 8 h across 4 channels | Controlled recording + in-frame clock |
| R-02 | R-01's disk filled to force overwrite | Known aged-out recordings — real-world T2/T3 oracle |
| R-03 | Hikvision-family unit, same protocol | As R-01 |
| R-04 | CP Plus unit | **Tests the doc 4 claim that CP Plus ≡ Dahua family** |
| R-05 | TP-Link VIGI unit | Filesystem-based path |
| R-06 | Uniview unit | RE validation |
| R-07 | Matrix SATATYA unit | RE validation |
| R-08 | Any unit, pulled from field service (unknown history) | Realistic dirty data; no full ground truth — used for crash/robustness only |

### 3.3 Tier E — Export-file corpus

Vendor export files (`.dav`, `.264`, `.mp4`) produced by the units above, with the
matching on-disk recording known. Validates provenance class D handling and — usefully —
lets the `.dav` parser be validated **before** the disk parser exists.

### 3.4 Corpus governance

- Every corpus item has a `ground_truth.json` beside it in the documented schema.
- Corpus items are hashed and the hashes are in the repo; a changed fixture is a
  reviewed change.
- Real-device images may be too large for the repo: store externally, keep the hash and
  the ground truth in-repo, and have CI skip-with-notice when the image is absent.
  **A skipped test is reported as skipped, never as passed.**

Notation: **TC-<area>-<n>**. Each has ID, requirement traced, oracle, and pass criterion.

is the most efficient defence against the confident-wrong-answer failure mode.

Test data policy: **no real case data, ever, in the corpus or the repo.** All Tier R
images come from team-owned hardware recording team-produced content.

## 6. Entry and exit criteria

**Entry to formal validation (per milestone):** the milestone's FRs are implemented;
unit tests pass; the relevant corpus items exist with ground truth; the build is
version-tagged.

**Exit / release gate — all must hold:**

- [ ] All **P0** requirement test cases pass
- [ ] **AC-01 … AC-13 all pass**
- [ ] TC-ID-01…07: **zero false-confident misidentifications**
- [ ] TC-AQ-03: zero writes to evidence
- [ ] TC-IN-01: 100/100 tamper trials detected
- [ ] TC-RB-07: zero crashes/hangs/confident-wrong across 10,000 fuzz cases
- [ ] TC-RP-06: determinism verified
- [ ] TC-ML-01: network isolation verified
- [ ] Every timestamp decoder has passing known-good vectors (NFR-12)
- [ ] Known limitations documented in §8 **and reflected in the tool's own output**
- [ ] Validation report signed by the test owner and reviewed by an examiner

A P1/P2 failure is recorded as a known limitation, not a blocker. **Any P0 failure, and
any confident-wrong-answer failure at any priority, blocks release.**

## 8. Known-limitations register (living)

Maintained continuously, published with every release, and — critically — **mirrored in
the tool's own output** so an examiner cannot use an unsupported path without being told.

| # | Limitation | Affects | Surfaced to user by |
|---|---|---|---|
| L1 | Matrix / Honeywell-native supported at carve-only level | FR-25, FR-26 | Identification screen states support level |
| L2 | Unknown layout versions are not parsed | FR-03 | Warning + automatic carving fallback |
| L3 | Carved items without frame-header timestamps have no absolute time | FR-45 | "Time unknown" label everywhere it appears |
| L4 | Vendor codec variants may not decode with the bundled FFmpeg | FR-35 | Detected and reported per recording |
| L5 | Live logical acquisition cannot verify source integrity | FR-16 | Provenance class C stated in the report |
| L6 | Third-party exports: completeness unverifiable | FR-18 | Provenance class D stated in the report |
| L7 | Analytics are leads, not identifications | FR-96 | Disclaimer on every hit |
| L8 | Encrypted vendor storage is detected, not defeated | doc 1 §8 | Explicit message and report entry |
